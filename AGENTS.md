Built in Cursor, deployed on Vercel (preset vercel). No Lovable sync.

## Architecture

- Profiles and targeted news use scoped mock services; news validates consent/audiences and returns family-safe fields plus receipts. Due schedules release on reads using a separate fixture clock, never background jobs.
- Plans use a scope-keyed mock subscription service with legacy normalisation; Pro capabilities are checked without deleting data, and Opus subscription invoices stay separate from family invoices.
- The teacher enrolment details form is a presentational question flow over the existing onboarding service; later intake, welcome and activation stages retain their service-owned validation.
- Onboarding and libraries are scope-keyed session services; activation deep-copies template sections, items and milestones, while parent intake always derives family ownership and omits teacher diagnostics.
- Assignment services enforce plan, family consent and guardian review approval; async delivery is occurrence-keyed separately from attendance, and policy credits are idempotent ledger entries rather than cancellations.
- Shared controls wrap on phones and dialogs stay within the dynamic viewport; the weekly timetable stacks days on phones and uses columns on larger screens to avoid page-wide horizontal scrolling.
- Screens read/write only through async functions in src/services/ (one file per area) over fixtures in src/mocks/ — so the mock layer can be swapped for a REST API later.
- App shell (nav rail / bottom tabs, role switcher, larger-text toggle) lives in src/routes/__root.tsx via AppShell; role switch swaps teacher app for parent portal there. Below 640px the header tools (language, tour ?, larger text, help, plan, sign out / demo selects) sit in `#app-header-tools` behind a Menu toggle; they stay in the DOM so `data-tour` targets still exist. The parent portal does not repeat the logo or studio name (the shell header shows them). `/login` has no language switcher (Andrew, 19 Nov 2026): languages are on marketing pages and inside the app only.
- New-teacher mode is a separate root role gate over setup-only session fixtures and namespaced queries; it never mounts demo teacher screens or mutates demo collections. Setup selects a state calendar and saves partial progress; imports use a separate new-studio roster and chat store, never demo collections.
- Student import uses Papa Parse and pure row validation; the async import service revalidates on commit, groups by normalised guardian email, stores batch IDs for idempotency and sends only in-app chat invitations. Demo imports populate roster and weekly slots; new-studio imports remain separately scoped.
- Demo scheduling resolves effective-dated weekly rules and stable-ID one-off exceptions before availability checks; credits use an append-only occurrence-keyed ledger, and booking atomically reserves a slot and debits the balance before chat notification. Existing isolated new-studio setup remains separate from demo scheduling.
- Route loaders prime TanStack Query through mock services; attendance optimistically updates the date-keyed cache with rollback so marking is immediate without bypassing the service layer.
- Live lessons are keyed by occurrence ID; the lessons service composes curriculum and chat services, retains notes in mock session state and sends an idempotent family summary. Readiness uses weighted section-average course stages; practice uses the lesson's Monday–Sunday week and separates student and teacher logs.
- Chat uses a shared list/detail layout and service-backed query caches; attachments use session object URLs and voice playback is simulated, keeping the prototype mock-only. Summary metadata identifies lesson cards without parsing message copy. New message timestamps follow the future-dated fixtures so newest-first ordering remains reliable. Teacher translations read mock English mappings through the chat service and never replace original messages.
- Billing derives Term 2 quantities from timetable weekdays and the shared calendar, stages one session draft per family, and sends idempotently into mock invoices. Only drafts apply current studio tax registration; all issue paths freeze registration, title and reconciled line/total taxes, and issued reads preserve those stored values; the GST setting invalidates invoice caches for both prototype views.
- Parent mode mounts a separate family portal inside the root role gate, keeping teacher routes unmounted and preserving the teacher location on return. Parent services resolve the mock guardian, scope every read/write to that family and return no risk fields; bilingual UI uses src/i18n JSON and reuses chat media/composer with guardian authorship.
- Teacher Students uses roster/profile services to compose schedule, curriculum and family invoices; attendance covers term-to-date with session overrides, while practice charts use four complete seven-day periods ending yesterday. Check-in navigation passes a student ID, validates family ownership in the service and prefills only the teacher composer without sending.
- Client notes have a dedicated mock collection and async service; teacher lesson sheets share the same student/family note context. Parent services explicitly select shared notes for their own family and strip guardian contact numbers from every response.
- Payment records are the source of truth for amount paid and invoice balances; both teacher and parent mock payment actions settle only the remaining balance and retain method/date records.
- Renewals keep independent Term 2–4 session campaigns with own-family parent responses and idempotent invitations plus manual/simulated reminders in family chat; no background job runs. Billing remains Term 2 only and gates on its campaign confirmations, never another term’s responses.

- Integrations use scope-keyed session mock states and async services only; billing stores Xero sync timestamps on issued invoices and new payment records, while parent online payments enforce Stripe status in the service as well as the UI. New-studio integration queries and state remain isolated from demo billing.
- Curriculum services own course edits and append-only checkpoint feedback over mock course fixtures; pure helpers calculate stage readiness and attended-occurrence reminders, and parent responses explicitly select course fields and shared comments to prevent private feedback leakage. Legacy requirement APIs remain for fixture compatibility, not displayed readiness.
- Live auth: Art Deco `/login`, Supabase Google/Microsoft/email OTP + required staff TOTP MFA; platform admin (`platform_staff`) and `/admin` console; mock mode unchanged when Supabase env is absent. See `docs/security/auth.md`.
- Family portal on real studios: parents' lessons (next 28 days), news meant for them and their children's active courses (shared feedback only) come from `familyPortalFn` (`src/server/family-portal.ts`, service key scoped to the verified user's own guardian row and family; rules pure in `src/lib/family-portal.ts`) and are loaded into the parent stores by `src/services/live/family-store.ts`. Never give guardians a direct read on staff tables for this. See `docs/security/family-portal.md`.
- Enrol wizard progress (0024): Students → Enrol steps 2-4 (welcome checks/ratings, starting stages, template, hours, minutes, target term, practice goal, strengths, work-on) are saved per student in `enrolment_progress` (staff-only RLS, one row per studio+student, answers jsonb) by `saveLiveEnrolmentProgress` in `src/services/live/enrolment-store.ts` before `saveEnrolment` changes the store, and laid over the intake draft at sign-in (`applySavedProgress`). Activation marks the row active (kept as the welcome record). A missing table only logs a warning. Target terms come from `onboardingTermOptions()`/`paceTerms()`/`defaultTargetTerm()` in `src/lib/onboarding.ts` (today's term + 4 for real studios; the demo keeps its fixed 2027 list). Assignments are still demo-only, so activation skips the first-week assignment list on real studios.
- Practice logs and client notes (0023): staff load and save through `src/services/live/notes-store.ts` (RLS, staff only). Parents log practice through `familyLogPracticeFn` and get only shared notes in the family portal copy. `curriculum.addPractice` and `notes.addNote/updateNote/deleteNote` save to Supabase first on real studios.
- Family onboarding is the first Supabase-backed slice; invite tokens are hashed and verified server-side with the service role; acceptances and consents are append-only; mock mode remains the default when Supabase env vars are absent.
- Tenancy: RLS through app_private helpers (narrow, owned by tenancy_helper); service-key server code must call requireStudioRole; role operations as in 0003's header; tests in supabase/tests/tenancy.test.sql must pass before merge. Media limits are enforced by Storage buckets and confirmUpload, not the phone. No polling. Video links are off until reviewed. Live family payments run only through Stripe Connect (0021, below).
- Subscription access (0006): one flat subscription per studio in `studio_subscription`; RESTRICTIVE `access_gate_*` RLS policies on every studio table, and `requireStudioRole` checks access (402 `studio_paused`; `access: "read"` lets a paused studio's owner read, `"skip"` is for billing only). Stripe billing webhook `/api/stripe/billing-webhook` (not Connect), daily suspension job, MSA 12.2 rules. Rules live in `src/lib/subscription.ts` and must match `app_private.studio_access_level`. See `docs/security/subscription-access.md`.
- Onboarding tours: a studio tour (teacher shell, mounted in `__root.tsx`) and a family tour (parent portal, EN + 中文 + VI). The family tour's first card asks who is taking it: "I'm the student" runs `STUDENT_TOUR` (student wording, no invoices) and "I'm a parent or guardian" runs `FAMILY_TOUR` (`familyTourSteps`, choice kept in `keystone.tour.v1.family.audience`). Students have no login of their own yet (ADR-022 proposed), so both paths run on the family sign-in. Steps live in `src/lib/tour-steps.ts` and point at `data-tour` attributes on existing elements; keep those attributes when restyling a screen (`src/test/onboarding-tours.test.tsx` checks they exist). Progress goes through `src/services/tour.ts` (localStorage now; the person's own profile row later). The family tour waits while a terms update is open. The studio tour runs in setup order (details, terms, privacy, payments, invoices, enrol, courses, news, chat) and its last card offers the setup guide (`SETUP_TOUR`), a second provider that wraps it so the ? button still replays the studio tour.
- Help centre (0007): FAQ articles in `src/lib/help/articles.ts` (studio EN; family EN + 中文) — only describe live features. Public `/help`, in-app `/support`, family portal Help view. Support requests go through `src/server/support.ts` (verified identity or Turnstile, rate limit, `support_request` table, email to SUPPORT_EMAIL). Family lesson/fee/progress questions route to the studio chat, not Keystone. See `docs/security/support-requests.md`.
- Lesson calendar (0010): `/calendar` reads and writes `lesson_series` (weekly or one-off lesson per student, local date/time in `studio.timezone`) and `lesson_exception` (one week cancelled or moved) through `src/server/calendar.ts`; rules are pure in `src/lib/lesson-calendar.ts`. "Change from this week on" ends the old series and starts a new one. Other server code that saves a student's weekly time calls `addLesson(actor, studioId, input)`. Google Calendar is a one-way push to a Keystone-created calendar (`calendar.app.created` scope, refresh token in Vault via `calendar_connection`); event ids derive from our uuids, and a failed push never fails the lesson change. See `docs/security/calendar.md`.
- Studio snapshot (Phase 1): `/snapshot` for owners/admins only — week/month tiles (Australia/Sydney) over invoice payments, overdue, roster, incomplete invites, practice-at-risk and lessons delivered; drill lists + CSV via `src/services/snapshot.ts`. Demo `studioStaffRole` gates the nav; teachers stay on Today without whole-studio revenue.
- Pro CFO (Phase 3): same `/snapshot` owner/admin gate — CFO pulse (net cash, margin, unearned tuition, Xero+GST health), revenue/churn + make-up $ liability, Xero queue retry, teacher remittance/export, overdue chat chaser, GST $75k radar via `src/services/pro-cfo.ts` over mock Stripe/Xero; not live 2-way Xero or BAS lodging.
- Tax Lite / Accounting Lite (Phase 2): same `/snapshot` owner/admin gate — YTD or AU FY (1 Jul–30 Jun) pack via `src/services/tax-lite.ts` over `src/mocks/tax-lite.ts`; billable pass-throughs append `lineKind: "reimbursement"` to family drafts; Stripe gross/fees prefer stored payment fields then labelled derived estimates; home-studio hours from timetable + admin at ATO 70c/hr; optional km log; EOFY CSV. Not a general ledger or Xero 2-way sync.
- Marketing pages: public `/welcome` and `/pricing` (listed in `PUBLIC_PAGE_PATHS`, no session, no app shell). Prices and the Base cap come from `PUBLIC_PLANS` in `src/lib/plans.ts`, whose cap is `BASE_STUDENT_CAP` in `src/lib/subscription.ts` (30, matching the 0017 trigger). Finance previews read `src/services/marketing-finance.ts` mocks only. Lovable no longer syncs to main; port its `lovable-sync` branch by hand.
- Releases: follow `docs/release-process.md`. Migrations are expand-only and backward compatible with the code live now; drops/renames go in a later migration marked `-- release: contract`. Never edit a migration already on `main`. New migrations (0007+) need `supabase/rollbacks/NNNN_name.rollback.sql`. `node scripts/check-migrations.mjs` must pass. Add a CHANGELOG line under Unreleased.
- Studio workspace (0011): a live sign-in to a studio that is not `studio.is_demo` empties the in-memory fixtures (`src/mocks/clean-studio.ts`) and fills them from that studio's own rows (`src/services/live/studio-store.ts`, user session + RLS, no service key). Saves go to Supabase first, then the store; a failed save never shows as saved. Saved today: invoices, lines, payments, credit notes, invoice events and billing settings on the 0004 tables (`src/services/live/billing-store.ts`; public billing services are wrapped in `withLiveBillingSave`, which runs them one at a time, diffs the store and saves; services that call other billing services use `billingInternals`, never the wrapped exports, or the queue deadlocks; numbers only from `send_studio_invoice` / `issue_studio_credit_note_number` (0016); dates from `src/lib/studio-clock.ts`), student courses as one jsonb document per course + studio-made Library items (0015, `src/services/live/course-store.ts`, `withLiveCourseSave` snapshots and restores the course arrays; real students get an unsaved empty starter course, never `seedStudentCourse`), news posts + manual student groups (0014, `src/services/live/news-store.ts`; `newsNow()` is real time for live studios), family chat (0013 `conversation`/`message`, append-only except `read_at`, `src/services/live/chat-store.ts`), studio details (`studio.name` + `studio.profile` jsonb), published studio terms (`terms_version`), families, guardians, students, the deletable example student. Not saved yet (empty for real studios): lessons, assignments, practice logs. Billing emails (invoice, receipt, credit note, reminders, late fee and pause notices, bank details changed) go through `sendBillingMail` (`src/services/billing-mail.ts`): real studios call `sendBillingEmailFn` (`src/server/billing-email.ts`), which checks staff role + MFA, only sends to that studio's guardians (bank-detail notices go to the owners), renders the email on the server from `billingEmailTemplates` with the studio name from the database, and sends through Resend from `EMAIL_FROM` as "<Studio> via Keystone Music HQ" with the studio's reply-to; the demo and tests use the mock outbox. A failed billing email never undoes the invoice or payment; it adds an `email_failed` event to the invoice. New ids in a live studio must be uuids (`newRecordId`). Never send invites to `isExample` families. The demo studio is set with SQL only (`update studio set is_demo = true`).
- Parents and the studio row: guardians have no RLS read on `studio` (0003). `chooseStudioWorkspace` gets a parent's studio from `guardianStudioFn` (`src/server/guardian-studio.ts`: verified user -> own guardian row -> studio, profile without `termsDraft`). A parent never falls back to the demo fixtures; if their studio can't load they get the "Your studio didn't load" screen. Live family invites (`enrolAndInviteStudent`, resend) refuse until the studio has a published studio agreement.
- Public site languages: marketing pages stay English in source/SSR; `useSiteTranslation` (mounted by `MarketingNavbar`) swaps visible text after mount from English-keyed dictionaries in `src/i18n/marketing/`. When adding marketing copy, add its zh-CN and vi entries; wrap legal text and help articles in `data-no-translate`. Why: one copy source, no hydration mismatch.
- Languages (public site and signed-in app): English stays the source in components and SSR. `useSiteTranslation` (mounted once in `RootComponent`, `src/routes/__root.tsx`) swaps visible text, `aria-label`, `title`, `alt` and `placeholder` after mount from English-keyed dictionaries: marketing copy in `src/i18n/marketing/`, app copy in `src/i18n/app/` (`"English": ["中文", "Tiếng Việt"]`, `{name}` patterns, en-AU dates), then the setup-wizard dictionary. When adding UI copy, add its zh-CN and vi entry in `src/i18n/app/`; `src/test/app-i18n.test.tsx` checks placeholders. Put `data-no-translate` on anything people write (chat, news, notes) and on legal text and help articles. Textareas are never translated. Why: one copy source, no hydration mismatch, and no per-component string plumbing. See `docs/i18n.md`.
- Notification emails (0018): `/api/cron/notifications` runs every 15 minutes from Supabase pg_cron + pg_net (Vercel free crons are daily only). Unread chat (15 min, once per chat until read, both directions), important news straight away, 7am studio-time summary of other news + shared feedback; quiet 9pm-7am; `NOTIFY_DAILY_LIMIT` cap (Resend free 100/day). Candidates come from service-only SQL functions `notify_*_candidates`, `notification_log` stops double sends, `notification_preference` is each person's own switches + unsubscribe token. Emails never carry message text or a child's name (Andrew, 11 Nov 2026). Templates in `src/server/email/templates/notification.ts` copy the frame of `supabase/templates/magic_link.html`. See `docs/security/notifications.md`.
- Stripe Connect (0021): studios link their own Stripe account through Account Links (Stripe-hosted onboarding, full Stripe Dashboard, Stripe handles pricing; no OAuth client id). Families pay invoices with Stripe Checkout as a direct charge on the studio's account (`Stripe-Account` header), no application fee. Server code in `src/server/stripe-connect.ts` (owner + MFA to link/unlink, guardian of the invoice's family to pay, amount owing computed on the server); `/api/stripe/connect-webhook` (Connected-accounts endpoint, `STRIPE_CONNECT_WEBHOOK_SECRET`) records the `payment` row (unique per PaymentIntent) and invoice status. Never record a Stripe payment from the browser. The demo studio keeps the simulated Stripe flow. See `docs/security/stripe-connect.md`.
- Xero sync (0022, Pro only): owner + MFA connects through OAuth (`src/server/xero.ts`, signed state, `/api/xero/callback`, granular scopes); tokens in Vault via `xero_connection_*` (service role), refresh under the 0003 lease. One-way push of sent invoices, family contacts and payments every 15 minutes (`/api/cron/xero-sync`, pg_cron) and on Sync now; ids stored in `invoice.xero_invoice_id` / `payment.xero_payment_id` / `family.xero_contact_id` so nothing is sent twice. New connections stop at `XERO_MAX_CONNECTIONS` (default 5 = Xero's free tier); never raise it without Andrew. The demo studio keeps the simulated Xero. See `docs/security/xero.md`.
